# 只更新指定文章

## 什么时候用

只想公开某篇文章的新修订，而其他文章的新稿尚未准备好时使用。未选的已发布文章保留上一份成功快照。

## 开始前

已有成功发布版本。假设 A、B 已公开，A 本地还有未发布修改，本次只想更新 B。

## 操作步骤

1. 保存 B 的正文与资源，检查并预览 B。

   ```sh
   npm run blog -- check <文章B>
   npm run blog -- dev --post <文章B>
   ```

   检查并预览本次真正要修改的文章。

2. 进入发布菜单，只勾选 B，不勾选 A。

3. 看计划确认 B 属于本次选择，A 属于保留旧快照。

   ```sh
   npm run blog -- publish <文章B> --dry-run
   ```

   selected 只包含 B，A 在 unchanged 中。

4. 不要靠修改 draft 标志或全量扫描来决定公开集合。

5. 重新选择执行，核对全站基线变化并确认。

   ```sh
   npm run blog -- publish <文章B>
   ```

   明确执行 B 的修订，不附带其他草稿。

6. 上线后核实 B 的新修订，以及 A 仍使用旧文字、封面、图片和轮廓。

### 同名替换图片，也必须重新发布文章

如果 B 引用 `./assets/photo.jpg`，用新图片覆盖同名文件后保存并检查 B。图片字节变化会生成新的修订 / 媒体哈希；明确选择 B 发布，公开页才会指向新资源。A 的同名图片位于另一个文章目录，既不会被 B 覆盖，也不会顺带更新。

如果改的是 `src/assets/avatar/` 或 `src/config/profile.json`，那是全站基线，不是 B 的本篇素材；即使只选择 B，代码与个人资料变化仍需单独接受，见[基线更新](/release/baseline)。

### 发布后发现遗漏了 C

先等本次发布核实完成，再保存、检查 C 并只选 C 开启下一次发布。旧公开的 B 自动保留；不要为了“补一篇”把所有草稿重新勾上。若 Pages 仍排队，先检查 Actions 和 status，不绕过 PAGES_PENDING。

## 确认结果

公开集合是旧成功清单加 B 冻结修订，其他文章不会顺带刷新。

## 影响与取消

Git 备份里的 A 可以有新原稿，但公开 A 仍是旧快照。发布与全部写作备份不是同一件事。

## 常见问题

如果 B 链接了 C 草稿，需要明确将 C 纳入发布或移除链接。缺 A 旧快照时必须恢复持久数据；服务器可通过 recover 取回公开包，Pages-only 不能从网页自动重建旧快照。
