# 接受全站基线变更

## 什么时候用

修改全站代码、头像、共享资源或构建配置后使用。这类变化可能影响整站，不能当成只更新一篇文章处理。

## 开始前

修改了网站代码、头像、配置、依赖锁或媒体转换流水线。未选文章仍应保留旧源快照。

## 操作步骤

1. 先完成本地代码检查、构建或视觉验收。

2. 查看发布计划，确认 baselineChanged 与候选文章范围。

3. 交互向导会单独询问是否接受全站代码／配置更新；默认取消。--yes 不能暗中接受该扩大影响。

4. 参数模式只有核对后才添加 --accept-baseline。

5. 再次核对发布确认，执行冻结与上线。

6. 核实新代码／头像和未选文章的旧正文；服务器单目标必要时可按整站版本回滚。启用 Pages 时自动 rollback 暂不支持，见[回滚边界](/release/rollback)。

### 哪些变化属于全站，哪些只属于一篇

| 变更 | 影响范围 | 如何公开 |
| --- | --- | --- |
| 某篇正文、tags、cover、flow、media.yaml、本篇引用图片 | 该文章修订 | 明确选中这篇文章 |
| profile.json、头像、共享插画、页面 / 样式代码 | 全站代码与资源 | 单独接受 baseline，再核对整站 |
| 依赖锁、构建命令、Node / 平台 / 图片工具 / FFmpeg 基线 | 构建可复现性 | 在匹配环境验收后接受，不改旧冻结对象 |
| deploy、Git / Pages 连接目标 | 交付位置 | 核对目标；更换远端不等于自动迁移全部历史 |

`codeRef: null` 使用当前工作区；设置 Git codeRef 后，受其约束的网站文件来自指定 Git 版本，未提交的那些修改可能不会进入基线。没有根 Git 仓库时保持 null。这里的“接受”不是提交 main，也不是自动升级依赖。

### 安全的执行顺序

先跑 `npm run check`，再预览改到的页面；用 `build <文章> --dry-run` 查看范围，明确接受后做本地构建。最后 publish 时仍核对实际候选计划，因为 dry-run 和实际执行之间保存了文件，基线就可能变化。

仅加 `--yes` 不能跳过 baseline 检查。未核对时让操作停止是正常保护；不要编辑 codeHash 或旧包 checksums.json 使它“看起来没变”。

## 确认结果

新公开版本使用新代码基线，但没有被选中的文章文字和资源仍取旧快照。

## 影响与取消

这不是单篇元数据更新。依赖锁必须与本地安装基线匹配；旧包可用于回滚。

## 常见问题

旧计划重建时流水线变化可能被阻止。恢复原版本或重新计划，不篡改旧冻结代码与校验摘要。

## 参数方式

尖括号是占位符，应换成实际文章或目录，不要原样执行。未安装简短命令时用 `npm run blog --`；已安装时可替换成 `blog`。

```sh
npm run blog -- publish <文章> --dry-run
npm run blog -- publish <文章> --accept-baseline --yes
```
