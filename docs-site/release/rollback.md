# 整站回滚

## 什么时候用

新版本出现问题，想让整个网站恢复到某个历史成功版本时使用。它不是单篇撤销，也不覆盖当前本地写作。

## 开始前

已有服务器成功发布版本，且没有启用 pages。回滚恢复整站代码与全部文章，不是撤销单篇本地编辑。

::: warning 当前支持范围
自动 rollback 只支持 deploy 服务器目标，包括本机验收部署器。Pages-only 不支持；同时配置服务器与 Pages 时也会拒绝，避免只回滚一端。不要通过临时停用 Pages 把双端操作伪装成单端回滚。
:::

## 操作步骤

1. 先查远端状态和历史，确认当前与目标版本。

2. 进入“整站回滚 · rollback”，从成功发布记录选择目标。

3. 先看计划里的 from、to、restored、removed，核对将恢复和消失的公开文章。

4. 重新进入执行，核对计划并确认，默认取消。

5. 服务器在锁下比较基线，切换目标并检查健康；并发变化会拒绝。

6. 查询远端版本，在浏览器检查文章和资源；本地写作文件保持原样。

### 回滚会让什么改变

例如 R1 公开 A，R2 在 A 之外新增 B。将 R2 回滚到 R1 后：A 恢复 R1 的文字、图片和整站代码，B 不再出现在当前网站；本地 A 的新稿与 B 原稿仍在。计划中的 restored 表示目标版本包含的条目，removed 表示当前有而目标没有的条目。

回滚不重新转换资源，也不采用当前头像 / 个人资料。需要仅修正某篇文章时，优先编辑并[发布指定修订](/release/update)，不用整站回滚来代替。

### 执行后先核实，再继续写作发布

查询服务器确认 current 指向目标版本，打开主页和恢复后的文章、媒体、下载附件。需要再公开 B 时，从已核实的回滚版本规划一次新的明确发布。并发发布导致基线变化时重新查看计划，不强制覆盖。

## 确认结果

返回 DEPLOYED 与目标版本。旧 HTML 可继续请求其版本化静态资源。

## 影响与取消

所有公开页面、代码和资源回到指定版本，本地新稿不被覆盖。

## 常见问题

结果 UNKNOWN 先核实，不能把 SSH 中断当作回滚失败。没有成功历史时不能凭任意目录回滚。

Pages 需要纠错时，当前 CLI 可以明确发布一个新的修正版；历史重部署与本地发布记录对齐尚无自动回滚流程，需单独规划，不能假设 rollback 已支持。[Pages 能力边界](/setup/github-pages)。

## 参数方式

尖括号是占位符，应换成实际文章或目录，不要原样执行。未安装简短命令时用 `npm run blog --`；已安装时可替换成 `blog`。

```sh
npm run blog -- rollback --to <release-id> --dry-run
npm run blog -- rollback --to <release-id> --yes
```
