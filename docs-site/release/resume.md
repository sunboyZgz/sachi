# 继续中断的冻结发布

## 什么时候用

已经冻结发布计划，但构建或上线中断时使用。继续原计划不读取后来修改的新稿，先核实是否其实已成功上线。

## 开始前

已有实际执行时保存的冻结计划。只看计划的预演不产生可恢复计划。先核实服务器当前状态。

## 操作步骤

1. 先执行 status --remote，判断网站是否已经切到目标版本。

   ```sh
   npm run blog -- status --remote
   ```

   先核实是否已经上线，避免重复创建新版本。

2. 进入“继续冻结发布计划”，选择尚未完成的本地 release-id。

3. 先看恢复计划，核对目标 ID 与服务器基线。

   ```sh
   npm run blog -- publish --resume <release-id> --dry-run
   ```

   使用实际已保存冻结计划的完整 ID，不传预演 ID。

4. 重新进入并确认执行。完整包可复用，构建失败时可从冻结源和代码重建。

   ```sh
   npm run blog -- publish --resume <release-id>
   ```

   核对原目标并确认；恢复不读取后续草稿。

5. 不要同时选择新文章，也不把后来修改的正文当作原计划内容。

6. 结束后核实服务器版本与记录。

### 先分清卡在哪个阶段

| 情况 | 应使用什么 | 原因 |
| --- | --- | --- |
| 只执行过 dry-run | 重新选择文章并规划 | 没有保存可恢复的冻结计划 |
| 已保存计划，构建中断，尚无完整包 | `publish --resume <release-id>` | 使用原代码、原 Markdown 与素材重建 |
| 服务器单目标，上传 / 切换中断 | 先 status --remote，再 resume 同一 ID | 不引入 Pages，不读取后来的新稿 |
| 含 Pages，完整包交付部分失败 | 修复后 `push <release-id>`，保留原目标覆盖参数 | 重试两个钩子，成功目标不回滚 |
| Git 已推送，Actions 构建或部署失败 | 检查 Actions 日志，重跑对应失败作业 | 同包 push 不产生新的 push 事件 |
| 服务器已经上线，只是 Git 记录未同步 | `sync` 补记 | 不需要再发布文章 |

不要把“重新运行 publish 并选择相同文章”当成 resume：重新发布会生成新 ID，并读取当前修订。原包已经冻结后继续编辑不会混进 resume，但新计划会采用那些修改。

### release-id 到哪里找

优先使用实际执行时终端输出的 ID 和报错中的重试命令。也可查 `history` 的本地记录；构建尚未完成时，查看 `.blog-store/plans/` 中已保存计划的文件名。**只读查看，不编辑它们**。没有实际保存的计划或完整包，就不能从预演 ID 继续。

恢复执行前核对原目标。曾用一次性的 `--pages-remote`，重试也要指定同一仓库；它不会成为永久配置。Pages-only 的已排队包不要靠 resume 绕过 PAGES_PENDING，先核实 Actions，或按上表重试完整包。

## 确认结果

成功完成同一冻结 release-id。服务器基线已改变会拒绝旧计划恢复。

## 影响与取消

不重新读取当前文章修订。中断不是重新发布全部草稿的理由。

## 常见问题

BUILD_ONLY 和已完成 DEPLOYED 记录不在待继续菜单中。流水线改变导致拒绝重建时恢复原流水线或重新规划，不修改校验文件。

远端已换成别的成功版本时，旧计划会被拒绝；先核实当前网站并重新规划，不强行覆盖。换电脑、Node、系统平台或媒体工具后重建旧计划也可能被拒绝，保留原环境或使用已校验的完整包；不要修改描述文件伪装环境一致。
