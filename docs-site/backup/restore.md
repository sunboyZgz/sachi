# 从 Git 恢复到新目录

当前项目的完整私有备份使用[私有资料仓库](/backup/store)：原稿与历史统一在 `.blog-store/`，通过 `npm run backup` 提交推送。原 `blog sync/restore` 仍兼容内容分支格式，两者不是同一份仓库布局。

## 什么时候用

本地写作丢失，且独立 Git 内容仓库中有备份时使用。恢复到新目录后核对内容，再决定如何迁回项目。

## 开始前

已配置内容仓库。准备尚不存在的专用目录，不使用当前项目、祖先目录或主目录。

## 操作步骤

1. 进入“从 Git 恢复到新目录 · restore”。

2. 输入新目录绝对路径，例如 /你的工作目录/sachi-writing-restored；不要直接复制此占位示例。

3. 先看计划中的目的目录与远端。

   ```sh
   npm run blog -- restore --destination <新的绝对目录> --dry-run
   ```

   替换为尚不存在的新目录，核对来源与目标。

4. 重新进入执行，核对后确认，克隆内容分支。

   ```sh
   npm run blog -- restore --destination <新的绝对目录>
   ```

   确认后恢复到新目录，原工作目录不覆盖。

5. 检查文章、原素材和身份，先在新目录验收，再由你决定如何合并回写作目录。

### 目录怎样填才安全

目标必须**尚不存在**，不是“已有但空的文件夹”。例如项目在 `/工作目录/sachi`，可选择它旁边新的 `/工作目录/sachi-writing-restored-01`；路径是示意，应替换为你的绝对路径，带空格时用引号包住。

restore 克隆已配置的内容分支，不是根项目 main / Pages blog 分支。恢复目录通常能看到 content、templates、内容配置；若曾做过发布备份，也可能有 `.snapshots` 与 `.release`。这些不是公开站点，不能把整个恢复目录挂到静态服务器。

### 恢复后怎样迁回

1. 先保留当前项目和恢复目录，不直接覆盖 content。
2. 按文章 id 比较同一篇的正文、assets 和 media.yaml，不能只凭文件夹日期判断最新版本。
3. 明确决定采用哪份修订，再将该篇完整目录放入正式固定栏目；避免重复 id / slug 与同名目录覆盖。
4. 运行 check，再 dev 预览。公开网站状态另用 status --remote 核实，恢复原稿不会自动公开。

这个合并过程由你决定，CLI 不自动解决两台设备的文本 / 二进制素材冲突。恢复目录是内容仓库，不含完整网站依赖，不能直接在其中运行博客开发服务器。

## 确认结果

返回 RESTORED 与目录。不恢复网站源代码，不覆盖当前写作。

## 影响与取消

新目录可能包含全部已备份草稿；不要把恢复目录直接作为公开静态根。

## 常见问题

目标已存在时拒绝。根项目没有 Git 不影响从独立内容仓库恢复，但 git 配置和 Git 工具仍需要。
